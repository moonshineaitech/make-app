# How an app works

On Windows and Linux, the generated file contains a small Rust launcher, the matching desktop runtime, a compressed project snapshot and inferred project settings. The launcher validates its settings and runtime with SHA-256 and caches the runtime by content hash. Linux can extract the embedded AppImage runtime without requiring FUSE. macOS output copies the converter application bundle, keeps its framework links relative, adds the project payload and metadata and applies a local ad-hoc signature; publisher signing/notarization is separate.

Packaging prepares a temporary source snapshot, includes installed dependencies and bundles a verified managed runtime or a supported compiled artifact. Missing dependencies and required builds are prepared in that snapshot. The original project is preserved. Dot-env files, private keys, version-control folders and common caches are excluded. Ignored prior release and scratch directories are omitted unless an explicit runtime path requires them. Unsupported self-contained runtime combinations are refused.

At first launch, the app verifies and extracts its payload into private writable application storage. Its saved commands use that extracted project and bundled runtime; the original project folder and Make App installation are not required. Later launches reuse the completed snapshot. Each recipient has separate writable files and state. Share the single Windows EXE or Linux run file, or zip the complete macOS app bundle. Output must match the recipient's OS and architecture. Windows single-file output is limited to 2 GB. External services, credentials, hardware and OS libraries remain application requirements.

Launchers generated before standalone packaging was introduced retain their original behavior and must be regenerated to become portable. Opening a project directly in the converter still detects its live setup and can provision missing runtimes; that mode is separate from opening an exported standalone app.

Direct launchers optionally cache content hashes using file identity, size, modification and change times. Changed entries are rehashed; strict native-permission checks always read content freshly. Cache failures fall back to content reads. The cache is an optimization, not an execution trust boundary or security sandbox.

Web projects open their own desktop window with managed local services. Native GUI apps retain their own windows. Tools get streamed output/input and supported interactive terminals. Windows uses Job Objects; macOS/Linux use controller-owned process groups and PTY cleanup. Independently daemonized POSIX processes can escape that group, so lifecycle ownership does not isolate arbitrary hostile programs.

Web export instead copies an existing static frontend build into a new directory and adds browser installation metadata, raster/SVG icons and scoped offline caching. That output can be served over HTTPS to phones, tablets and computers. Native/backend code, databases, credentials and external services require their own host and setup.
